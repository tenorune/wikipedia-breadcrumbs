Deliverable 1 — Optimization & Refactoring

Top priority

1. Sync path does per-record network round-trips HIGH (verified)

packages/shared/src/sync/supabase-backend.ts:35–46 · packages/shared/src/sync/engine.ts:67–95 · packages/pwa/src/lib/stores/sync.svelte.ts:45–52, 82–92

SupabaseBackend.upsertAll() upserts one record at a time in a loop. Supabase accepts an array, so a sync of 100 trails + 500 visits makes ~600 HTTP requests where ~2–3 would do. The same N+1 pattern repeats locally: the sync engine marks each record Synced with an individual update() call (use Dexie bulkUpdate/bulkPut), and the PWA sync store re-stamps every trail/visit in a per-row loop (use Collection.modify()).

Caveat when batching: the current code tracks per-record success, and a batched upsert returns one error for the whole batch — chunk the array (e.g., 500 rows) and fall back to per-record only on chunk failure. This is the single biggest performance win in the codebase.

2. PWA reloads everything after every mutation HIGH

packages/pwa/src/lib/components/TrailList.svelte:38–72, 104–198 · TrailDetail.svelte:204–262 · routes/+page.svelte:105

TrailList fetches all trails, then fetches visits per trail (N+1), and this full loadTrails()/loadData() reload re-runs after every star toggle, note edit, delete, and merge. Dexie ships liveQuery() for exactly this — reactive subscriptions would eliminate both the N+1 and the manual-reload pattern in one refactor, and would also remove the three duplicate visibilitychange reload listeners spread across +page.svelte, TrailDetail.svelte, and TrailList.svelte.

3. ~60–70% component duplication between extension and PWA HIGH

packages/extension/src/history/{TrailDetail,TrailList,VisitCard,ImportDialog}.svelte vs packages/pwa/src/lib/components/ equivalents

TrailDetail (533 vs 659 lines), TrailList (336 vs 447), VisitCard (276 vs 345), and ImportDialog (essentially 100% identical) exist in both packages — roughly 650+ lines of duplicated logic, so every bug fix must be applied twice. Both packages already build Svelte 5: extract a shared UI package (or packages/shared/src/ui/) and inject the two things that actually differ — navigation strategy (message-to-background vs goto/target="_blank") and DB mutation strategy — as callback props. Start with ImportDialog (trivial), then VisitCard, then the two big ones. This also unblocks decomposing the 659-line PWA TrailDetail into TrailHeader / NoteEditor / MergeDialog / VisitList.

4. Service worker has no update flow, and the offline fallback looks broken HIGH (verified)

packages/pwa/src/service-worker.ts:9, 43

The precache list is [...build, ...files] — it does not include prerendered, yet the offline navigation fallback does caches.match("/index.html"), which will likely return undefined (the as Promise<Response> cast hides this from the compiler). So the advertised “full offline support” plausibly fails on a cold navigation. Separately, there is no skipWaiting/update-prompt flow, so users keep running the old bundle until every tab is closed.

Fixes: add prerendered to ASSETS, remove the unsafe cast, and add a “new version available — reload” toast driven by the waiting worker.

5. Concurrency and error-swallowing in the PWA sync/auth stores HIGH (verified)

packages/pwa/src/lib/stores/sync.svelte.ts:66–78 · auth.svelte.ts:16–56

syncNow() has no in-flight guard — the 5-minute interval and a manual sync can run engine.syncNow() concurrently (if (_syncing) return; is a one-line fix). On failure it only console.errors; _lastReport is never updated, so the UI cannot show that sync failed (pairs with UX quick win #1). The auth store has a related init race: onAuthStateChange is registered before OAuth-redirect processing completes, which can flip _loading early and double-register the visibility-refresh handler.

6. Extension capture flow is chatty and fragile across service-worker restarts MEDIUM

packages/extension/src/background/capture.ts:68–190, 213–308 · background/index.ts:196–213

Each Wikipedia navigation triggers 5–17 sequential sendToOffscreen() round-trips — batch these into one composite “recordNavigation” message. Two MV3 lifecycle issues: (a) idle alarms persist across service-worker termination but the in-memory trailManager doesn’t, so when the alarm fires after a restart the trail is silently never finalized — query the offscreen DB instead of memory on alarm fire; (b) the 1.5-second title/redirect setTimeout has no per-tab cancellation, so rapid navigation lets a stale response overwrite a newer visit.

Medium priority

  • Type safety in the sync path — multiple as any casts in engine.ts (lines 69, 83, 126, 138–139) and untyped Record<string, unknown> field mapping in field-mapper.ts, where a field accidentally listed in LOCAL_ONLY_FIELDS silently vanishes from sync. Worth tightening given this code guards data integrity.
  • Full-table scans — language-badges/index.ts:28–42 loads all visits into memory to extract distinct languages; export (export-json.ts, export-csv.ts) fetches trails and visits one-by-one instead of bulkGet + one indexed visits query; hasPendingChanges() in the PWA sync store uses .filter() (scan) rather than an indexed where("syncStatus").
  • Duplicated store logic in shared — visitStore and trailStore have near-identical update() sync-status logic and identical softDelete() — extract shared helpers.
  • Duplicated displayName derivation — three PWA components compute it with slightly different fallbacks (“Empty trail” vs “…”) — extract getTrailDisplayName(trail, visits) into shared.
  • Reconciliation is O(n·m) — reconcileActiveTrails() (background/index.ts:37–123) fetches all visits per active trail every 15 minutes just to read the last one — add a getLastVisit(trailId) query.

Low priority

  • JSON.parse(JSON.stringify(...)) cloning in import-json.ts:175–194.
  • Menu-close $effect listeners registered via setTimeout in TrailDetail.svelte:66–86 (leak-prone).
  • export * from in shared/src/index.ts exposing internals like toSnakeCase as public API.
  • No pagination/virtualization on the trail list (only matters at 500+ trails).
  • Each extension history component instantiating its own BreadcrumbsDB.

Deliverable 2 — Features & UX

Quick wins (small effort, high value)

  1. Surface sync errors. Directly enabled by fixing code finding #5 — today a failed sync is indistinguishable from a successful one. Add an error state to SyncStatus.svelte and the settings page.
  2. Accessibility pass. Only ~20 ARIA attributes across the whole PWA; the “⋮” icon menus in TrailList/VisitCard/TrailDetail have no labels, and dialogs don’t restore focus on close. The README advertises WCAG AA — this closes the gap cheaply.
  3. Search within a trail. Global search exists but a 50-page trail has no way to jump to a page. The search logic already exists in TrailList — reuse it in TrailDetail.
  4. Undo toast for deletes. Deletes are already soft (deletedAt), so a 10-second “Undo” toast is mostly UI work — the data model already supports it.
  5. PWA update notification — falls out of service-worker fix #4 above.
  6. Loading skeletons + empty-trail call-to-action in trail detail (currently content pops in and empty trails dead-end at “No visits in this trail.”).

Medium bets

  1. Manual capture (/add route) in the PWA. Already in the project backlog (docs/superpowers/specs/2026-03-31-pwa-auth-design.md). Highest-leverage feature on the list because it attacks the core platform gap: the PWA can’t capture visits at all — paste one or more Wikipedia URLs, pick/create a trail. The URL parser already lives in shared.
  2. Mobile share target. Add share_target to manifest.webmanifest feeding the /add route — on Android, “Share → Breadcrumbs” from any browser becomes the mobile capture story. Small once #7 exists.
  3. Stats dashboard. The home page shows three counts; the data (timestamps, positions, parentVisitId link graph, languages) supports trails-per-week, longest chains, most-revisited pages. Motivates sustained use.
  4. Discovery-tree view. parentVisitId already records which page led to which; the extension popup shows relation markers but the PWA renders a flat list. Even simple indentation would show the research narrative — the full graph visualization can come later.
  5. Keyboard shortcuts — chrome.commands for start/end trail in the extension; list navigation in the PWA. Explicitly deferred to “Phase 1.5” in the design docs.
  6. Extension install upsell from the PWA — the empty state says “install the extension” with no link to the Web Store.

Strategic (large effort)

  1. Public trail sharing (/shared/[id]). The visibility: "public" enum already exists in the model and the design docs defer this. It’s the feature that makes trails a shareable artifact (“here’s my research path”) rather than a private log — and the natural growth loop for the product.
  2. Overlay/sidebar on Wikipedia itself. The design doc flags this as blocked on mockups. Seeing and annotating the trail without leaving the page is the biggest possible UX jump for the extension.
  3. Sync conflict resolution UI. Conflicts are logged to conflictLogs but no UI ever shows them — multi-device users experience silent last-write-wins. A minimal viewer (what was overwritten, restore option) covers most of the value.
  4. Article metadata enrichment — thumbnails/summaries via the Wikipedia API would make trail review far more scannable, and enables richer citations.

Suggested sequencing

A practical order: batch the sync upserts + add the syncNow guard and error surfacing (items 1/5 + UX 1) → fix the service worker offline/update issues (4 + UX 5) → adopt liveQuery in the PWA (2) → extract shared UI components starting with ImportDialog (3) → then build /add + share target (UX 7/8), which changes what the PWA fundamentally is.

Appendix A — Shared library (packages/shared)

Full agent report — 15 findings

Performance issues

1. Sync Engine — N+1 database updates HIGH
packages/shared/src/sync/engine.ts:67–74
In the push() method, trail records are updated individually in a loop instead of batch updating. Same for visits (lines 80–88) and conflict logs (lines 91–95).

for (const result of results) {
  if (result.success) {
    await trails.update(result.id, { syncStatus: SyncStatus.Synced } as any);
  }
}

This creates multiple database round-trips proportional to record count. Fix: implement a batch update method in stores or use Dexie's bulkUpdate() API. Impact: on a sync with 100 trails + 500 visits, this is 600+ individual update operations instead of 2–3 batch operations.

2. Supabase Backend — individual upserts HIGH
packages/shared/src/sync/supabase-backend.ts:35–46
upsertAll() performs individual upsert calls in a loop instead of batch upserting.

for (const record of records) {
  const { error } = await this.client.from(table).upsert(record);
}

Supabase supports batch upsert (array of records), so this is a missed optimization. Fix: change to await this.client.from(table).upsert(records) (pass entire array). Impact: reduces N network round-trips to 1, major performance win on larger syncs.

3. Export functions — full-table scans with N+1 queries HIGH
packages/shared/src/export/export-json.ts:4–20 · export-csv.ts:23–39
When exporting specific trails (with trailIds param):

if (trailIds) {
  const all = await Promise.all(trailIds.map((id) => db.trails.get(id))); // N separate queries
}

Then for each trail, fetches visits separately:

for (const trail of trails) {
  const visits = await db.visits.where("trailId").equals(trail.id)...toArray(); // N separate queries
}

This is O(n+m) where n=trails, m=visits. Fix: use the existing compound index on [trailId+position], batch-fetch trails with db.trails.bulkGet(), and fetch all relevant visits in one query grouped by trailId. Impact: reduces database query count from O(n+m) to O(2) for typical export operations.

4. Language badges — full-table scan without index MEDIUM
packages/shared/src/language-badges/index.ts:28–42
getDistinctLanguages() loads ALL visits to memory, filters, and sorts:

const visits = await db.visits.filter((v) => v.deletedAt === null).toArray(); // Full table scan
visits.sort((a, b) => a.timestamp.localeCompare(b.timestamp)); // In-memory sort

This loads potentially thousands of records just to extract distinct languages. Fix: use sortBy("timestamp") in the query chain, then iterate once to collect distinct languages. Impact: eliminates unnecessary memory allocation and in-memory sorting; reduces latency on large datasets.

5. Language badge settings — repeated full-table scan MEDIUM
packages/shared/src/language-badges/index.ts:9–21
getLanguageBadgeSettings() always loads the first visit even when settings are cached:

const settings = await db.languageSettings.get("default");
if (settings?.configured) return settings;
// But still always fetches first visit even if settings exist
const firstVisit = await db.visits.filter(...).sortBy("timestamp").then((visits) => visits[0] ?? null);

This full-table scan happens on every call if settings aren't marked as configured. Fix: cache the result or skip the full-table scan if settings?.configured is already true. Impact: reduces unnecessary full-table scans to a one-time initialization.

6. Trail operations — inefficient merge sorting MEDIUM
packages/shared/src/trail/operations.ts:26–45
In mergeTrails(), fetches visits from two trails, concatenates, and re-sorts by timestamp in JS:

const allVisits = [...primaryVisits, ...secondaryVisits].sort((a, b) => a.timestamp.localeCompare(b.timestamp));

Then updates each visit's position in a loop (lines 38–40). This is O(n log n) sort + O(n) updates. Fix: use database sorting directly and rely on the position parameter to maintain order. Impact: eliminates unnecessary in-memory sort and reduces code complexity.

7. Import JSON — repeated string validation overhead LOW–MEDIUM
packages/shared/src/export/import-json.ts:44–67
Validation has repeated .length checks and type checks for each field across nested loops. Sets like VALID_STATUS, VALID_VISIBILITY are created at module load, but could be optimized with a schema library. Fix: consider using a schema validation library (Zod, io-ts) to reduce boilerplate and improve maintainability. Impact: modest — improves code clarity and reduces bug surface, not necessarily runtime speed.

Refactoring issues

8. Type safety — unsafe any casts MEDIUM
packages/shared/src/sync/engine.ts:69, 83, 126, 138–139
Multiple uses of as any to suppress type errors:

await trails.update(result.id, { syncStatus: SyncStatus.Synced } as any);
const { id, ...changes } = remote as any;
await this.db.table(recordType === "trail" ? "trails" : "visits").add(remote);
losingSnapshot: { ...local } as any,

Fix: create proper generic types for the merge record function, or use strict typing for synced records. Impact: reduces risk of silent bugs in sync logic; improves maintainability.

9. Duplicate error handling logic in stores LOW
packages/shared/src/db/visits.ts:20–29 · db/trails.ts:24–35
Both visitStore() and trailStore() have nearly identical update() methods. Both check if the record is Synced and mark as PendingSync; both fetch the current record to get syncStatus.

let syncStatus = (changes as any).syncStatus;
if (syncStatus === undefined) {
  const current = await db.visits.get(id);
  syncStatus = current?.syncStatus === SyncStatus.Synced ? SyncStatus.PendingSync : current?.syncStatus;
}

Fix: extract into a shared utility function autoMarkSyncStatus(current, changes). Impact: reduces code duplication, easier to maintain sync logic.

10. Missing abstraction — similar deletion logic LOW
packages/shared/src/db/visits.ts:31–33 · db/trails.ts:42–44
Both softDelete() implementations are identical:

const now = new Date().toISOString();
await db.visits.update(id, { deletedAt: now, updatedAt: now, syncStatus: SyncStatus.PendingSync });

Fix: create a generic softDelete(db, tableName, id) utility. Impact: reduces duplication; one place to update deletion logic.

11. Unsafe recursive object manipulation in import LOW
packages/shared/src/export/import-json.ts:175–194
Uses JSON.parse(JSON.stringify(...)) to deep-clone and ensure clean objects. This is inefficient and fragile (loses functions, undefined values, circular refs). Object destructuring would be clearer. Fix: use explicit object construction with destructuring or a proper clone utility. Impact: improves performance slightly and reduces fragility.

12. CSV escape function — redundant logic LOW
packages/shared/src/export/export-csv.ts:11–21
The csvEscape() function checks for formula injection (/^[=+\-@]/) but also checks for quotes and newlines:

if (/^[=+\-@]/.test(str)) {
  str = "'" + str;
}
if (str.includes(",") || str.includes('"') || str.includes("\n") || str.includes("'")) {
  return `"${str.replace(/"/g, '""')}"`;
}

After prepending ', the second check will always quote, making the first check redundant for CSV safety. Fix: combine checks or clarify intent. If formula injection is a concern, handle it in the second pass. Impact: minor code clarity improvement.

13. Wikipedia URL parser — multiple regex evaluations LOW
packages/shared/src/wikipedia/url-parser.ts:53–59
isArticlePage() checks multiple prefix arrays sequentially. For every URL, it evaluates two Array.some() loops and a regex test. Fix: combine prefix checks into a single regex or use a trie (overkill for this size, but good practice). Impact: negligible for typical usage; good for high-volume URL parsing.

14. Type safety gap in sync field mapper MEDIUM
packages/shared/src/sync/field-mapper.ts
The field mapper functions are untyped and accept/return Record<string, unknown>. They don't validate that required fields are present after mapping.

export function mapToRemote(obj: Record<string, unknown>): Record<string, unknown> {
  const result: Record<string, unknown> = {};
  for (const [key, value] of Object.entries(obj)) {
    if (LOCAL_ONLY_FIELDS.has(key)) continue;
    result[toSnakeCase(key)] = value;
  }
  return result;
}

If a required field is accidentally in LOCAL_ONLY_FIELDS, it silently disappears. Fix: add type-safe mapping with explicit field lists or use TypeScript branded types. Impact: prevents silent data loss bugs in sync.

15. API surface — over-export of internal utilities LOW
packages/shared/src/index.ts
The public API exports all internal utilities (export * from "./sync/index.js", etc.), including internal functions like mapToRemote, mapToLocal, toSnakeCase, toCamelCase that are implementation details. If these are part of the public API, they constrain refactoring. Fix: re-export only intended public APIs; consider an _internal/ namespace. Impact: better API stability and flexibility for internal refactoring.

Appendix B — Chrome extension (packages/extension)

Full agent report — 16 findings

Performance issues

1. Redundant database reads in offscreen handler MEDIUM
packages/extension/src/offscreen/handler.ts:34, 45, 56
getActiveTrailForTab, getActiveTrailByUrl, and getActiveTrails all call trails.getActive(), which fetches all active trails from IndexedDB. Three separate handler cases (lines 33–57) repeat this pattern, scanning all active trails repeatedly even when only one result is needed. Lines 34–41 loop through all trails to find one by tabId; lines 45–53 loop through all to find by URL; line 56 returns all without filtering. Fix: create a helper getActiveTrailQuick(predicate) to exit early on first match; for getActiveTrails, cache results in-memory during the offscreen session or batch the queries. Severity note: only called on navigation/recovery, not per-page, but adds latency to trail detection.

2. Excessive offscreen messaging overhead in capture flow MEDIUM
packages/extension/src/background/capture.ts:68–190
Each Wikipedia navigation triggers 5–17 sequential sendToOffscreen() calls (add trail, add visit, find visit by URL, update trail, update visit, etc.). Each call requires an IPC round-trip + retry logic; lines 68–87 alone make 2–3 calls with retry delays (500ms × attempt). Lines 146–151 (findVisitByUrl), 156–160 (updateVisit), and 194–198 (updateTrail) make sequential calls that could batch. Fix: batch operations into single composite messages like { type: "recordNavigation", trail, visit, parentVisitId, existingVisit? } to collapse 5+ calls into 1–2. Impact: degrades UX on slow devices; repeated navigations compound latency.

3. Redundant visit recovery on every navigation MEDIUM
packages/extension/src/background/capture.ts:64–87
If a trail is not in trailManager memory, the code attempts 2–3 DB lookups (getActiveTrailForTab, getActiveTrailByUrl, then URL-parsing recovery). The service worker can wake multiple times per session, but after the first recovery the trail should be in memory; repeated recoveries waste DB reads (lines 64–87 recover even if just recovered 100ms ago). Fix: skip recovery if the trail was recovered within the last ~10 seconds (add a timestamp to ActiveTrailEntry); for SW restart, reconcile on startup only once.

4. setTimeout-based title/redirect polling in capture LOW
packages/extension/src/background/capture.ts:213–308
After each navigation, a setTimeout(1500ms) fires to fetch page title and redirect info from the content script. If the user rapidly navigates (e.g., 3 links in 2 seconds), multiple 1.5s timers overlap, and late responses from older navigations can corrupt newer visits. No deduplication by tabId; capturedTrailId and capturedUrl are captured but never validated against the current page. Fix: store active pending timers per tabId and cancel on new navigation; validate the response matches current tab state before updating. Primarily affects redirect detection.

5. Unoptimized trail reconciliation on startup LOW
packages/extension/src/background/index.ts:37–123
reconcileActiveTrails() runs every 15 minutes (lines 31, 196–199). For each active trail it fetches ALL visits (line 56: getVisitsByTrailId) just to get the last one and check URL matches. With 100 trails × 50 visits each this is O(n·m) DB reads; lines 55–87 also loop through all visits again to find matches by URL (nested loop, O(n²) worst case). Fix: create a getTrailLastVisit(trailId) method; batch trail updates.

Refactoring opportunities

6. Component duplication: VisitCard across extension and PWA MEDIUM
extension/src/history/VisitCard.svelte (276 lines) · pwa/src/lib/components/VisitCard.svelte (200+ lines)
Nearly identical component logic (formatTime, note editing, citation copying, card menu) with minor differences: extension navigates via a navigateActiveTrail message to background; PWA opens target="_blank". Timestamp formats differ slightly. Both share identical note autoresize, citation format list, and menu-closing logic. Estimated duplication: ~70% of code (~150 LOC). Fix: extract to a shared UI package; leave only the navigation strategy different via a callback prop.

7. Component duplication: TrailList across extension and PWA MEDIUM
extension/src/history/TrailList.svelte (336 lines) · pwa/src/lib/components/TrailList.svelte (200+ lines)
~65% overlap in structure: both have search input, sort dropdown, data menu (export/import), and trail list rendering; both have identical import/export logic, conflict dialog, and formatDate. Differences: extension initializes db locally, PWA gets it from a store; extension uses an onSelectTrail callback, PWA uses goto(). Estimated duplication ~200 LOC. Fix: extract to shared package; inject navigation strategy via callback or context.

8. Component duplication: TrailDetail across extension and PWA MEDIUM
extension/src/history/TrailDetail.svelte (533 lines) · pwa/src/lib/components/TrailDetail.svelte (400+ lines)
~60% overlap: both implement edit name/note, star toggle, focused visit view, sort (discovery/visited), merge UI, split/export; identical VisitCard integration, language badge logic, and timestamp formatting. Differences: extension sends messages to background, PWA directly mutates DB; extension uses an onMutated callback. Estimated duplication ~250 LOC. Fix: extract shared container/presenter logic; inject the DB mutation strategy. Largest component; most complex state management.

9. ImportDialog nearly identical across packages LOW
extension/src/history/ImportDialog.svelte · pwa/src/lib/components/ImportDialog.svelte
100% duplicate logic (parseImportJson, detectConflicts, executeImport); the only difference is const db initialization (local vs store). Fix: merge into one component in the shared package, inject db via prop/context. Trivial to extract.

10. Repeated getDeviceId() initialization LOW
extension/src/background/index.ts:19 · history/ImportDialog.svelte:63 and others
Each component re-instantiates BreadcrumbsDB() and calls getDeviceId() independently; Svelte components create 8+ DB instances across the history page. Fix: create a global store or singleton in an extension shared module for device ID and DB instance. Minor — IndexedDB access is cached, but unnecessary re-opens.

MV3 anti-patterns & correctness issues

11. Reconciliation alarm periodicity may fail under service-worker suspension MEDIUM
packages/extension/src/background/index.ts:31
A reconciliation alarm is created with periodInMinutes: 15. Chrome MV3 does not guarantee the alarm fires exactly; if the SW is terminated before the alarm triggers, it fires on next SW wake-up but could miss the scheduled time, with no recovery mechanism if skipped. Fix: on each onStartup (and periodically, e.g., on message from popup), check whether the last reconciliation was >15 min ago and run if needed. Stale trails may persist longer than intended.

12. Idle trail finalization dependent on transient state MEDIUM
packages/extension/src/background/index.ts:14, 196–213
Idle alarms are created per-tab, but if the service worker is terminated before the alarm fires, the alarm persists in Chrome's alarm store while the in-memory trailManager entry is lost. On next wake-up the alarm fires but trailManager.getActive(tabId) returns undefined (lines 207–211 silently skip), so the trail is never finalized. Fix: on alarm fire, query the offscreen DB for the active trail by tab ID before finalizing, or persist idle-alarm metadata to chrome.storage. Trails can remain "active" indefinitely if the SW restarts before idle timeout.

13. Message listener return value inconsistency LOW
packages/extension/src/background/index.ts:216–225
Line 224 returns true to indicate an async response, but line 221 returns false for the linkClicked message. If the linkClicked callback were async, returning false could cause a race where navigation fires before linkClicked is processed. In practice link click is processed synchronously before webNavigation fires, but MV3 best practice requires explicit async handling. Fix: return true and handle linkClicked asynchronously, or ensure ordering with a queue.

14. Tab ID tracking lost on browser restart LOW
packages/extension/src/background/index.ts:93–123
reconcileActiveTrails() re-associates trails with tabs after browser restart (tab IDs change). If a trail's last-visit URL was on a tab closed before restart, it matches no open tab; the trail is then considered "stale" if older than 2× idle timeout (lines 107–117) — a heuristic that could finalize active trails incorrectly. Fix: mark trails "stale but resumable" instead of finalizing; restore only on explicit user action. Edge case, but can create data-loss perception.

Type-safety gaps

15. Loose typing in offscreen messages LOW
packages/extension/src/offscreen/index.ts:16–22
Auth and sync handlers cast the request to req as any, losing type safety; a mismatch between message type and payload won't be caught at compile time. Fix: define separate typed functions per handler, or use discriminated unions with proper type narrowing.

16. Missing null checks in visit parent tracking LOW
packages/extension/src/background/capture.ts:162–178

Appendix C — PWA (packages/pwa)

Full agent report — 15 findings

High severity

1. High re-render cost from N+1 DB queries in TrailList & TrailDetail HIGH
packages/pwa/src/lib/components/TrailList.svelte:38–72
In loadTrails(), fetches all trails with ts.getAll() then iterates over each trail to fetch visits: await Promise.all(all.map(async (t) => { const visits = await vs.getByTrailId(t.id); ...})) — classic N+1. With 100 trails this runs 1 + 100 DB queries; each re-render after star/delete triggers a full reload. Fix: create a bulk getVisitsByTrailIds() in the shared lib or batch queries in a single pass, or use Dexie's liveQuery() to observe changes reactively instead of manual reloads.

2. Repeated full data reloads after every mutation HIGH
TrailDetail.svelte:204, 218, 229, 234, 243, 252, 262 · TrailList.svelte:104, 113, 198
After each update (toggle star, delete visit, update note, merge trails), full loadData()/loadTrails() is called, re-fetching all trails and visits. Severe performance cliff on devices with many trails; blocks UI during expensive re-renders. Fix: use Dexie liveQuery() for reactive subscriptions or implement optimistic updates + minimal invalidation (a star toggle only needs to update local UI + one DB record).

3. TrailDetail component is 659 lines — oversized & unmaintainable HIGH
packages/pwa/src/lib/components/TrailDetail.svelte:1–659
Handles trail name editing, note editing, merge UI, sort state, focused view, export, all visit-list rendering, and deletion. Multiple concerns mixed: editing state (editingName, editingNote, nameValue, noteValue), merge state (showMerge, mergeTargetId, mergeTargetLabel), menu states (detailMenuOpen, mergeDropdownOpen). Hard to reason about reactivity, difficult to test. Fix: extract <TrailHeader> (name, star, meta), <TrailNoteEditor>, <MergeDialog>, and <VisitList> (with its own sort logic), reducing the main component to ~150 lines with independently testable pieces.

4. Service worker cache strategy has no expiration or versioning HIGH
packages/pwa/src/service-worker.ts:25–48
Uses cache-first (caches.match() then fetch). Cached files are never expired or revalidated; CACHE_NAME uses version from build, but if the version doesn't change, stale assets serve forever. No stale-while-revalidate or max-age; assets cached at install never update. Users can get stuck on old app versions after deploys. Fix: stale-while-revalidate for mutable resources; strong versioning; background invalidation of old caches; serve index.html with no-cache headers. [Synthesizer's note: partially corrected — SvelteKit's version changes per build by default; the verified issues are the missing prerendered assets in the precache (offline fallback returns undefined) and the absent update-prompt flow.]

5. Race condition in auth state during OAuth redirect HIGH
packages/pwa/src/lib/stores/auth.svelte.ts:16–56
After OAuth redirect (lines 24–45), the store sets up an onAuthStateChange listener (line 18), then manually processes the token from the URL hash (lines 24–38), then calls replaceState and sets _initialized=true (lines 40–42). But the listener is registered at module load, so it may fire before _initialized=true, causing _loading to be set false prematurely (line 20: if (_initialized) _loading = false;). Also, _setupVisibilityRefresh() (lines 44, 55) can be called twice if the listener fires. Fix: register the listener only after the _initialized check, or use a one-time bootstrap listener plus a separate persistent listener.

6. Sync engine not protected from concurrent syncNow() calls HIGH
packages/pwa/src/lib/stores/sync.svelte.ts:66–78
syncNow() checks if (!engine) return; and sets _syncing = true, but doesn't check whether a sync is already in progress. If called twice rapidly (manual sync + 5-min interval in the same window), both enter engine.syncNow() concurrently, risking data races; the sync report can be corrupted by the second call overwriting the first. Fix: add if (_syncing) return; before _syncing = true.

7. sortedVisits recalculates on every state change MEDIUM

const sortedVisits = $derived.by() sorts the entire visits array on relevant changes with no memoization; sorting 1000+ visits repeatedly is wasteful and causes lag on large trails. Fix: strict dependencies so it recomputes only when visits, sortField, sortDir change; consider toSorted() or a derived cache key.

8. Sync store silently drops errors without surfacing MEDIUM
sync.svelte.ts:70–77
syncNow() catches errors and logs to console, but _lastReport is never updated on error — the UI shows no indication that sync failed. No retry logic. Fix: update _lastReport with error state; expose syncError in syncState; add exponential backoff retry; log to error tracking.

9. Memory leak: menu event listeners not reliably cleaned up MEDIUM
TrailDetail.svelte:66–86
Merge dropdown and detail menu each have an $effect() that registers a click listener via setTimeout() before adding it. Rapid toggling can accumulate listeners; cleanup timing is fragile. 10. TypeScript type-safety gap in component props MEDIUM
VisitCard.svelte:5–13, 157
Props include optional onSplit?: (position: number) => void but the component calls onSplit!(visit.position) after a truthiness check; showLanguageBadge?: boolean defaults implicitly. Fix: stricter prop types and explicit defaults in $props destructuring.

11. Duplicated trail display-name calculation MEDIUM
TrailDetail.svelte:170–176 · TrailList.svelte:50–57 · routes/+page.svelte:67–78
Three components independently compute displayName from trail.name or first/last visit title, with slight variations ("Empty trail" vs "…"). Fix: extract getTrailDisplayName(trail: Trail, visits: Visit[]): string to a shared utility.

Appendix D — Product / UX survey

Full agent report — 29 opportunities

UX gaps — missing states & error handling

(1) No sync error visibility in PWA. pwa/src/routes/settings/+page.svelte only shows authError for sign-in; sync errors from the engine are logged but never surfaced. The design doc docs/design/ui-ux-guidelines.md states the "app tells the truth" about status, but sync failures are invisible. Users can't distinguish "syncing," "offline," "sync failed with retry pending," or "sync succeeded" — creating uncertainty about data safety. Effort: small (error banner in SyncStatus component).

(2) No loading/skeleton states for trail detail pages. TrailDetail.svelte:88–93 · routes/trails/[id]/+page.svelte — loads trail data but renders immediately with no loading state. On slow devices or large trails, content shifts/jumps as data loads, violating the design principle "interface is stable" (ui-ux-guidelines.md). Effort: small (add a loaded state, render skeleton).

(3) Empty trail state in trail detail. TrailDetail.svelte:323 shows "No visits in this trail." with no button to add visits or guidance. Empty trails can exist after split operations or manual creation; the user has no next action. Effort: small.

(4) No undo for destructive actions. Delete trail (TrailList.svelte) and delete visit (VisitCard.svelte) both trigger soft-delete directly. The design doc says "destructive actions are deliberate" with confirmation, but there's no undo window. Even a 10-second "Undo" toast would prevent frustration; the soft-delete model already supports it. Effort: medium.

(5) No sync conflict resolution UI. Sync conflicts are logged to the conflictLogs table per the design spec, but neither the PWA settings page nor the extension has any conflict viewer or resolution flow. Multi-device users editing the same trail see silent last-write-wins data loss. Needs side-by-side comparison and restore. Effort: large.

UX gaps — mobile / cross-platform

(6) iOS PWA storage sync warning incomplete. routes/+page.svelte:49–51 detects iOS unshared storage and shows a prompt, but the flow to migrate data or explain isolation is unclear. Users install as an app expecting the same data as the browser — iOS isolates the storage, orphaning data. Effort: medium (educational onboarding + sync-before-install check).

(7) No keyboard shortcuts on either platform. Design spec 2026-03-30-chrome-extension-phase1-design.md line 382 lists "Keyboard shortcuts | Phase 1.5" as deferred; no keyboard nav in the PWA either. Power users can't quickly start/end trails, navigate, or trigger sync. Effort: medium (extension: chrome.commands; PWA: keyboard handlers).

(8) No touch-friendly confirmation dialogs on mobile. ConfirmDialog buttons are small (see VisitCard.svelte); no touch-device detection to enlarge targets. Tap accuracy is poor under 500px width — easy accidental confirms/cancels. Effort: small.

UX gaps — accessibility

(9) Limited ARIA labels in components. Grep shows only ~20 ARIA attributes across PWA Svelte files. Many icon buttons lack descriptions (the "⋮" menu buttons in TrailList, VisitCard, TrailDetail). Screen-reader users can't discover or understand menus, sort controls, or split/merge actions. Effort: small.

(10) No focus management on modal close. ConfirmDialog, merge pickers, and cite popovers close without returning focus to the trigger button. Per ui-ux-guidelines.md, "dismissing overlay should not trigger action on element beneath" — keyboard navigation breaks after closing dialogs. Effort: small (trap focus in dialogs, restore on close).

Feature opportunities — routes & capture

(11) Missing /add route in PWA (manual capture). Design spec 2026-03-31-pwa-auth-design.md line 367 lists "/add" in the backlog: "Manual capture — paste a Wikipedia URL or multiple URLs to add visits." PWA-only users can't create trails at all; manual URL entry enables desktop PWA use and bypasses browser capture restrictions. Effort: medium (URL parser, visit creator, trail picker, batch handling).

(12) Missing /shared/[id] route (public trail viewer). Design spec lines 212–213 mention SSR for shared trails; line 330 lists the visibility: "public" enum. No shared route exists (deferred per line 367). Users can't share research trails without manually copy-pasting each link. Effort: large (viewer, sharing UI, SSR setup, OG tags).

(13) No share-target handler for mobile. Design spec line 220 lists "Share Target"; the PWA manifest has no share_target (deferred per line 368). Mobile browsers can't capture Wikipedia — users can't share a page from another app into a trail. Major gap for mobile-first users. Effort: medium (manifest share_target + /add endpoint to receive payloads).

Feature opportunities — visualizations & analytics

(14) No trail timeline/map visualization. The data model includes timestamp, position, parentVisitId (link graph) but only flat lists are rendered. Visualizing navigation flow answers "how many digressions before returning?", "what's the longest linear path?", "which pages are most revisited?" Effort: large (D3 or similar, flow-graph layout).

(15) No statistics dashboard. The home page shows basic totals (trails, pages, notes) but no trends, comparisons, or breakdowns (trails per day, pages per trail, most-revisited pages). Motivates sustained use and goal-setting. Effort: medium (aggregate queries, chart component, date filtering).

(16) No search within trail (only global). TrailList has search but it's global; TrailDetail has none. Large trails (50+ pages) become hard to navigate. Effort: small (reuse TrailList search logic in TrailDetail).

Feature opportunities — visibility & metadata

(17) No trail activity timeline. Trails have updatedAt/createdAt but no activity log of when visits were added, notes changed, or trails split. Useful for edit history and replaying research chronologically. Effort: large (audit log table).

(18) No language-aware sorting or filtering. Language badges use visit.language, and settings have language exclusions, but trails can't be filtered by language ("English-only research", per-language stats). Valuable for researchers comparing language editions. Effort: medium.

(19) Missing breadcrumb hierarchy visual. parentVisitId enables tracking which pages were discovered from which; the extension's TrailView.svelte (lines 110–122) shows relation markers, but the PWA doesn't use it well and there's no visual breadcrumb chain. Essential for understanding the research narrative. Effort: medium (indentation/nesting in the visit timeline).

Feature opportunities — sync & multi-device

(20) No selective sync. The sync engine is all-or-nothing; no way to exclude old trails or pause sync for a specific trail. Enables "local research only" vs "shared research" and helps bandwidth-limited users. Effort: medium (per-trail sync flag).

(21) No sync scheduling. The PWA does a fixed 5-minute periodic sync with no user control (no night-only or WiFi-only sync). Battery/data savings on mobile. Effort: medium.

Feature opportunities — data quality

(22) No redirect detection / article metadata in PWA. The extension has redirect detection; Wikipedia API fetching is deferred to Phase 1.5 (spec line 381). The PWA has no access to redirects, summaries, or thumbnails — thumbnail + summary would make trail review faster and more visual. Effort: large.

(23) No citation metadata caching. Citations are generated on-the-fly from Visit fields with no capture of author/publisher/infobox data. Richer citations for academic use; automatic attribution for shared trails. Effort: medium.

Feature opportunities — extension-specific

(24) No overlay/sidebar mode on Wikipedia pages. The design doc says "overlay mode is a blocker for content script UI work and must be resolved via mockups" (2026-03-30-wikipedia-breadcrumbs-design.md line 192). Seeing trail state and taking notes inline without opening the popup would be a massive UX win. Effort: large.

(25) No multi-tab trail support. Trail-to-tab mapping is 1:1; opening the same trail in two tabs starts a new trail. Side-by-side article comparison and natural research forking need N:1 support. Effort: medium.

(26) No quick trail preview on Wikipedia links. No content-script feature to show "which trail does this page belong to?" on hover/right-click. Effort: medium.

Feature opportunities — PWA-specific

(27) No offline indicator for stale data. The app detects offline but only disables the sync button; it doesn't indicate which data is cached/stale. Effort: small (offline-mode banner).

(28) No extension install upsell from the PWA. The PWA home says "Install the extension to start browsing!" with no direct Web Store link or installation flow. Effort: medium (deep link, install verification).

(29) No PWA update notification. The service worker caches with no update prompt; users can run stale code for weeks. Effort: small.
